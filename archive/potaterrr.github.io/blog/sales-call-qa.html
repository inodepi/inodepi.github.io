The call is the evidence: building Sales Call QA

Nov 4, 2026 / 8 min read / 1,509 words / Christian John
n8nLLMSalesGuardrails
On this page

    Sales managers do not lack opinions about calls. They lack evidence. A manager hears one call on a Tuesday, remembers the worst sentence from it, and that becomes the coaching theme for the month. The rep who quietly improved never gets credit. The rep who had one bad call never hears the end of it.

    So I built Sales Call QA & Coaching: an n8n workflow that scores every finished sales call against the same five-part rubric, quotes the exact line behind every score, and only asks a human to look when the call is actually risky. Clean calls land in a data table and wait for Monday. Nothing is sent automatically.

    The interesting part was not the model call. It was deciding what counts as evidence, and what the workflow should do when the evidence is not good enough.

    The shape of it

    Eighteen nodes, one main line and one weekly branch:

    1. Retell posts the finished call to a webhook. A form accepts a pasted transcript for testing, so the pipeline works before a single real call exists.
    2. A Code node normalizes the payload, pulls out the rep and transcript, and refuses to score a call without a usable transcript.
    3. Gemini 3 Flash scores opening, discovery, objection handling, next step and compliance through a Structured Output Parser.
    4. A second Code node clamps the scores, recomputes the weighted overall, verifies every quote against the transcript, redacts emails and phone numbers, and picks the review path.
    5. Clean calls go to the Sales Call QA data table. Risky or low-confidence calls also become a Gmail draft for a manager.
    6. Every Monday, a digest reads the last week, aggregates it per rep, and files one coaching draft.

    The model gets one job: read the call and fill in five scores with evidence. Every decision that can be made deterministically — the weighted overall, whether the evidence is real, whether a human is required — happens in code after the model returns. That split is the whole design.

    The rubric

    Five dimensions, weighted to match what actually moves a deal:

    DimensionWeightWhat it checks
    Opening15%Name, company, permission to continue, a clear reason for the call without dumping the pitch.
    Discovery30%Situation, pain, impact, decision process and timeline. Confirms understanding before moving on.
    Objection handling25%Acknowledges the objection, explores it, answers with relevant proof, and checks whether the answer landed.
    Next step20%A specific date and owner, confirmed before the call ends. One if there is no next step.
    Compliance10%Recording disclosure where required, no guarantees, accurate pricing, do-not-call respected.

    Discovery carries the most weight because a beautiful pitch on top of a bad discovery is still a bad call. Compliance carries the least because most calls are boring on compliance — but it is a hard gate, not a suggestion: below 3 and the call always goes to a human.

    Rule one: every score quotes the call

    The first version asked the model for a score and a short justification. It produced lovely, plausible summaries that were occasionally about a different call. A score without a quote is just a vibe with a number.

    So the parser now requires an exact quote for every dimension, or the literal string no evidence in transcript. The validation node checks each quote against the normalized transcript. If fewer than three quotes verify, confidence drops and the call is forced into review. The model can still be wrong; it cannot be confidently wrong without a receipt.

    The first evidence check was too strict. Gemini quoted two lines and joined them with ..., which is a reasonable way to show an omission. The check compared the whole concatenated string against the transcript and failed. The fix was to split the evidence on ellipses and newlines, normalize each segment, and require every segment to appear:

    const parts = evidence
  .split(/\.\.\.|\n/)
  .map((p) => p.replace(/^(Rep|Prospect|Caller|Buyer|Customer):\s*/i, "")
    .toLowerCase()
    .replace(/[^a-z0-9]+/g, " ")
    .trim())
  .filter(Boolean);

return parts.length > 0 && parts.every((p) => transcript.includes(p));

    That is the kind of bug that makes a guardrail look broken when it is actually doing its job. The right response is to fix the ruler, not to loosen the rule.

    Rule two: do not punish an easy call

    The first rubric said objection handling was worth 25% and scored 1 if the rep did not handle an objection. Then a clean discovery call came through, the prospect agreed to everything, and the model gave the rep a 1 for objection handling. The rep did nothing wrong; there was simply no objection to handle.

    The fix is explicit in the prompt: if no objection is raised, score 3 and use no objection in transcript as the evidence. The rep is not punished for an easy call, and the manager is not sent a review draft about a call that went fine.

    This is a small rule with a big effect. Rubrics are opinionated. If you do not write down how the rubric behaves at the edges, the model will invent an answer, and it will usually be harsher than you meant.

    The review gate

    A call needs a human when any of these is true:

    • confidence is below 0.75,
    • the model raised any red flag,
    • compliance scored below 3, or
    • fewer than three quotes verified against the transcript.

    Everything else is a silent row in the data table. The risky path creates a Gmail draft with the red flag, the evidence and one coaching sentence. A manager reads the call, adjusts anything that looks off, and sends the note themselves. The workflow never sends the coaching email, the same way the invoice agent never sends the reminder and the lead retrieval agent never sends the check-in. Drafts are the boundary between automation and judgment.

    Bug one: the token budget ate the scorecard

    The first sales run returned an empty structured response. The parser reported invalid JSON, the agent reported MAX_TOKENS, and the completion token count was zero.

    The model had spent its entire output budget on reasoning before it reached the JSON. Four thousand tokens was not enough. Raising maxOutputTokens to 8192 fixed it. Same prompt, same call, valid JSON.

    This is the second time a token limit has looked like a schema problem. On a reasoning model, the output budget is a correctness setting. The failure shows up at the parser, which is the last place you would look. If a structured response is empty, check the finish reason before you rewrite the schema.

    Bug two: the Gmail credential expired, and the scorecard still had to land

    Halfway through testing, the Gmail credential expired. The first version saved the scorecard and then created the draft. That order meant a dead draft connection could throw away a perfectly good scorecard.

    Two changes fixed it. The save now happens before the draft, and the draft nodes continue with a regular output when they fail. On an expired token, the workflow logs the Gmail error, skips the draft, and keeps the row. The weekly digest still runs; the scorecard still exists; a human can reconnect the mailbox and pick up the drafts later.

    An automation should degrade, not disappear. If the notification layer is down, the data layer still has to do its job.

    What the demo does and does not prove

    The portfolio page includes a browser simulation. It reads a transcript, scores five dimensions, verifies evidence and shows the review path. It runs on a deterministic heuristic, not Gemini, and it never leaves the page.

    That is enough to show the shape of the product: the rubric, the quote check, the review gate, the Monday digest. It is not a benchmark, and it does not prove the model is right. The real workflow is the n8n build; the workflow JSON is there to import and point at a real Retell agent.

    What I would build next

    • Live Retell wiring. The webhook is in place; the next step is a real agent and a public n8n URL.
    • Score trends. A rep's five dimensions over eight weeks is more useful than any single call. The data is already in the table.
    • An objection library. Cluster the objections that get dismissed and attach the best responses. That turns a scorecard into a playbook.
    • AI SDR QA. Score the bot with the same rubric as the humans. If the bot gets a different standard, the comparison is marketing, not QA.

    The takeaway

    The hard part of call QA is not transcription, and it is not the model. It is deciding what counts as evidence and where the human boundary sits. A score without a quote is a vibe with a number. A quote that nobody checks is decoration. And a workflow that sends the coaching note itself has skipped the one step that makes the rest of it trustworthy.

    Score the call. Keep the human. That is the whole product. 🥔
